# 自动更新与发布设计

## 用户体验

启动完成后后台检查 GitHub 上的正式版本，发现新版时使用 Sparkle 的标准更新窗口显示版本与说明，允许下载、稍后提醒或跳过。Markdown 菜单提供“检查更新…”，手动检查会显示无新版或网络失败的结果。下载、验签、安装和重启由 Sparkle 处理；重启必须先通过文档保存检查，取消保存则不退出。

## 发布来源与信任

公开仓库 Singularity-Li/markdown 的 GitHub Releases 承载更新包和 appcast.xml，无独立服务器，无客户端 GitHub Token。固定入口为 releases/latest/download/appcast.xml，包 URL 指向明确 tag。版本比较使用单调递增的 CFBundleVersion，展示版本使用 VERSION。只发布 macOS 26+、Apple Silicon 构建。

Sparkle 固定依赖版本，框架嵌入唯一的根目录 Markdown.app。使用 Ed25519 对压缩包签名，App 内嵌公钥。私钥保存在 macOS 登录钥匙串，不写入仓库、App、日志或发布附件。更新包在解压前验证；仍保留现有 ad-hoc 代码签名，不宣称已 Apple 公证。

## 发布入口

Tony 说“发布新版本”即授权 Agent 完成整个正式发布流程。scripts/release.py 提供 prepare/publish/resume 操作；默认补丁版本递增，明确指定版本时遵循指定值。Agent 整理更新说明后运行流程：前置检查、测试、构建、打包、签名、提交、推送、创建草稿、上传验证、发布、公开下载验证。失败保留可恢复状态，不覆盖已发布版本，不强推，不混入其他改动。

开发构建只在根目录组装 Markdown.app，发布仅压缩该包。更新器在最终用户设备上的缓存、解压、临时替换属于运行时安装流程，不受开发产物位置限制。Sparkle 自带辅助程序是第三方框架内部组件，不是 Markdown.app 副本。

## 验证

自动化检查覆盖发布版本与附件规则、签名篡改、构建与包配置、文档退出保护。使用根目录 App 验证菜单、无更新提示和启动后台检查；跨版本安装测试必须保护未保存内容，只以根目录 App 为安装目标。未执行的跨机或系统授权测试如实标注。

## 实施顺序

1. 固定 Sparkle 依赖并配置嵌入、签名、公钥与 feed。
2. 接入启动检查、菜单入口及更新重启前保存检查。
3. 增加 VERSION、发布脚本、验证及失败恢复。
4. 更新 AGENTS.md 和 README，完成构建、真实菜单验证及发布链路核验。
